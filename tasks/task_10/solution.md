# Задание 10. Миграция на Cassandra

## Задание 10.1. Какие данные переносим в Cassandra и почему

### Чем Cassandra полезна в нашем случае

Сайт упал из-за того, что MongoDB при добавлении шардов перераспределяла все
данные и тратила на это ресурсы в пик нагрузки. Cassandra добавляет узлы без
полного перераспределения, не имеет единого мастера (запись принимает любой узел)
и очень быстро пишет данные.

Но у неё есть ограничения, которые определяют, что переносить нельзя:

- нет транзакций и строгой согласованности по умолчанию (данные актуальны не сразу);
- плохо переносит частые изменения и удаления одних и тех же записей;
- читает только по заранее известному ключу, без сложных запросов.

Поэтому в Cassandra хорошо ложатся данные, которые **много пишутся, почти не
меняются после записи и читаются по ключу**. Плохо - данные, где нужны
транзакции и точная актуальность (деньги, остатки).

### Критичные данные магазина

| Данные | Чем критичны |
| --- | --- |
| Заказы и оплата | целостность (деньги) |
| Остатки товаров | целостность (нельзя продать то, чего нет) |
| Корзина | скорость, пользователь сразу видит изменения |
| История заказов | большой объём и скорость чтения |
| Сессии пользователей | скорость, высокая частота |

### Что переносим в Cassandra

| Данные | Почему подходит |
| --- | --- |
| **История заказов** | Завершённый заказ не меняется, объём только растёт, читается по клиенту. Точная актуальность не нужна |
| **Сессии пользователей** | Простой доступ по ключу, очень частая запись, у Cassandra есть автоудаление по сроку (TTL). Строгая согласованность не нужна |

### Что оставляем как есть

| Данные | Почему не в Cassandra |
| --- | --- |
| Активные заказы и оплата | нужны транзакции и точная актуальность - остаётся в MongoDB |
| Остатки товаров | частое изменение с риском продать лишнее - остаётся в MongoDB |
| Корзина | очень частые изменения и удаления, пользователь должен сразу видеть результат - остаётся в MongoDB |
| Каталог товаров | проблема в объёме чтения, а не записи - закрывается кешем (Redis) |

### Итог

В Cassandra переносим **историю заказов** и **сессии пользователей**: они много
пишутся, почти не меняются и не требуют строгой согласованности. Деньги, остатки
и корзину оставляем в MongoDB, где есть нужные гарантии целостности.

Модель данных и ключи для этих сущностей - в задании 10.2, стратегии целостности -
в задании 10.3.

## Задание 10.2. Модель данных и ключи

### Как Cassandra распределяет данные

Cassandra хеширует partition key и по полученному числу (токену) кладёт партицию
на узел. Узлы делят между собой кольцо токенов. При добавлении узла к нему
переезжает только часть диапазонов токенов, а не все данные - в этом отличие от
MongoDB, которая перераспределяла всё. Поэтому ключ важно выбирать так, чтобы:

- значений было много и они были разнообразными - тогда данные лягут ровно по узлам;
- одна партиция не разрасталась до огромного размера ("горячая" партиция тормозит
  узел и читается медленно).

Модель строим от запросов: в Cassandra читать можно только по partition key, поэтому
сначала смотрим, как данные будут запрашивать.

### История заказов

**Запрос:** показать заказы клиента, сначала новые.

Логичный partition key - `user_id`: заказы одного клиента лежат рядом, читаются
одним обращением. Но у активного покупателя за годы накопятся тысячи заказов, и
партиция разрастётся. Поэтому добавляем в ключ "корзину" по году (`bucket`) -
партиция ограничена заказами за один год. Внутри партиции сортируем по
`order_id` (timeuuid) по убыванию, чтобы свежие заказы шли первыми.

```cql
CREATE TABLE order_history (
    user_id     uuid,
    bucket      int,          -- год, ограничивает размер партиции
    order_id    timeuuid,     -- кластерный ключ, хранит и время заказа
    created_at  timestamp,
    total       decimal,
    status      text,
    items       text,         -- позиции заказа в JSON
    PRIMARY KEY ((user_id, bucket), order_id)
) WITH CLUSTERING ORDER BY (order_id DESC);
```

- **Partition key `(user_id, bucket)`** - много клиентов и годов, токены лягут ровно,
  размер партиции ограничен одним годом, "горячих" партиций нет.
- **Кластерный ключ `order_id DESC`** - заказы клиента сразу отсортированы, выборка
  последних заказов идёт без дополнительной сортировки.
- Чтение за год - одна партиция: `WHERE user_id = ? AND bucket = 2026`.

### Сессии пользователей

**Запрос:** получить сессию по её идентификатору (по токену из cookie).

Partition key - сам `session_id`. Это случайный UUID, поэтому значения уникальны и
распределяются по узлам идеально ровно, "горячих" партиций быть не может. Кластерный
ключ не нужен: в партиции всего одна сессия. Срок жизни задаём через TTL - Cassandra
сама удалит протухшие записи, чистить вручную не надо.

```cql
CREATE TABLE user_sessions (
    session_id  uuid,
    user_id     uuid,
    created_at  timestamp,
    data        text,         -- содержимое сессии в JSON
    PRIMARY KEY (session_id)
) WITH default_time_to_live = 86400;   -- автоудаление через сутки
```

- **Partition key `session_id`** - случайный UUID, идеально ровное распределение.
- **TTL 86400** - сессия живёт сутки и удаляется автоматически.
- Чтение - точечное по ключу: `WHERE session_id = ?`.

### Почему это минимизирует решардинг

Обе таблицы используют partition key с большим числом разнообразных значений
(`user_id` + год, случайный `session_id`). Токены распределяются ровно, и при
добавлении узла переезжает только небольшая доля диапазонов - полного
перераспределения, из-за которого падал сайт на MongoDB, не происходит. Ограничение
размера партиции у истории заказов (год) и точечный доступ у сессий гарантируют, что
нагрузка не сконцентрируется на одном узле в пик.

| Сущность | Partition key | Кластерный ключ | Защита от горячих партиций |
| --- | --- | --- | --- |
| История заказов | `(user_id, bucket=год)` | `order_id DESC` | партиция ограничена годом |
| Сессии | `session_id` | - | случайный UUID, ровное распределение |

## Задание 10.3. Стратегии целостности данных

Cassandra пишет одни и те же данные на несколько узлов (реплик). Из-за сбоев и
отложенной записи реплики могут разойтись. Есть три механизма, которые их
выравнивают.

### Чем отличаются механизмы

| Механизм | Когда срабатывает | Цена |
| --- | --- | --- |
| **Hinted Handoff** | при записи, если реплика недоступна: координатор хранит "подсказку" и досылает данные, когда узел вернётся | дешёвый, работает сам |
| **Read Repair** | при чтении: координатор сверяет реплики и на лету чинит устаревшие | небольшая добавка к latency чтения |
| **Anti-Entropy Repair** | вручную или по расписанию (`nodetool repair`): полная сверка всех данных через дерево хешей | тяжёлый, грузит диск и сеть |

Логика выбора простая:

- Hinted Handoff и Read Repair - лёгкие и точечные, лечат только то, что пишется и
  читается прямо сейчас. Их держим включёнными почти всегда.
- Anti-Entropy Repair - тяжёлый, но единственный, кто чинит "холодные" данные,
  которые давно не читали. Нужен только там, где данные живут долго и их нельзя
  потерять. Запускать обязательно в пределах `gc_grace_seconds`, иначе удалённые
  записи могут "воскреснуть".

### История заказов

Данные важные (заказы терять нельзя), живут долго, часто читаются клиентом.

| Механизм | Решение |
| --- | --- |
| Hinted Handoff | **да** - если реплика лежит во время записи, заказ не потеряется и догонит узел при восстановлении |
| Read Repair | **да** - заказы регулярно читают, при каждом чтении реплики сами выравниваются почти бесплатно |
| Anti-Entropy Repair | **да, по расписанию** (раз в неделю) - старые заказы перестают читать, и Read Repair их уже не чинит; плановый repair выравнивает "холодные" партиции и не даёт расхождениям копиться |

Уровень согласованности - `LOCAL_QUORUM` на запись и чтение: большинство реплик
подтверждает операцию, клиент видит актуальную историю. Чуть выше latency, но для
просмотра заказов это некритично, зато нет риска показать неполный список.

### Сессии пользователей

Данные временные (TTL сутки), теряются без последствий - пользователь просто
перелогинится. Каждый запрос читает сессию по `session_id`.

| Механизм | Решение |
| --- | --- |
| Hinted Handoff | **да** - дешёвый и включён по умолчанию, лишним не будет |
| Read Repair | **да** - сессию читают на каждом запросе, чтение само поддерживает нужную реплику в актуальном виде |
| Anti-Entropy Repair | **нет** - данные и так удалятся по TTL через сутки; гонять тяжёлый repair по тому, что скоро исчезнет, - пустая трата ресурсов |

Уровень согласованности - `ONE` на запись и чтение: отвечает первая же реплика,
минимальная latency. Для сессий это оправдано - скорость важнее точной
согласованности, а редкое расхождение лечится повторным логином.

### Итог и компромисс latency / согласованность

| Сущность | Hinted Handoff | Read Repair | Anti-Entropy | Уровень согласованности | Приоритет |
| --- | --- | --- | --- | --- | --- |
| История заказов | да | да | да, по расписанию | `LOCAL_QUORUM` | надёжность важнее скорости |
| Сессии | да | да | нет | `ONE` | скорость важнее надёжности |

Главный рычаг компромисса - уровень согласованности. Чем больше реплик должны
ответить, тем выше гарантия и выше задержка. Поэтому для важных и долгоживущих
заказов берём `QUORUM` и добавляем плановый repair, а для временных сессий -
`ONE` без тяжёлого repair, ради минимальной задержки.
