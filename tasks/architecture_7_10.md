# Задание 7. Проектирование схем коллекций для шардирования данных

Раздел описывает схемы коллекций `products`, `orders` и `carts`, выбор
шард-ключей и стратегий шардирования с обоснованием под операции каждой
коллекции.

## Базовые принципы выбора шард-ключа

В MongoDB данные распределяются по шардам кусками (chunks) по значению
шард-ключа. Хороший шард-ключ должен давать:

- **Высокую кардинальность** - много различных значений, чтобы куски можно было
  дробить и распределять.
- **Низкую частотность** - ни одно значение не должно занимать непропорционально
  большую долю документов, иначе появляются jumbo-куски.
- **Отсутствие монотонного роста** - монотонно растущий ключ (например,
  `created_at` или `ObjectId`) направляет все вставки в один шард (hotspot).

Две стратегии шардирования:

| Стратегия | Как работает | Плюсы | Минусы |
| --- | --- | --- | --- |
| **Ranged (диапазонная)** | Куски по диапазонам значений ключа | Быстрые range-запросы и сортировка по префиксу ключа | Перекос и hotspot при монотонном ключе |
| **Hashed (хешированная)** | Куски по диапазонам хеша от ключа | Равномерная запись даже для монотонного ключа | Range-запросы по ключу становятся broadcast |

Запрос называется **targeted**, если содержит шард-ключ (или его префикс) -
тогда `mongos` идёт только в нужные шарды. Без шард-ключа запрос становится
**broadcast** и опрашивает все шарды.

## Коллекция products

### Схема

```json
{
  "_id": "ObjectId",
  "product_id": "string (uuid)",
  "name": "string",
  "category": "string",
  "price": "Decimal128",
  "stock": [
    { "geo_zone": "string", "qty": "int" }
  ],
  "attributes": {
    "color": "string",
    "size": "string"
  },
  "created_at": "Date",
  "updated_at": "Date"
}
```

### Операции и кандидаты в шард-ключ

Операции:

- Обновление остатка при покупке - очень высокая частота, по `product_id`.
- Карточка товара - высокая, по `product_id`.
- Поиск по категории и диапазону цен - средняя, по `category` и `price`.

| Кандидат | Кардинальность | Частотность | Оценка |
| --- | --- | --- | --- |
| `category` | низкая (десятки категорий) | высокая (категория "Электроника" огромна) | плохо: jumbo-куски, перекос |
| `price` | средняя | неравномерная (много дешёвых) | плохо: hotspot и перекос |
| `product_id` | очень высокая | равномерная | хорошо |

### Решение: hashed по `product_id`

```js
sh.enableSharding("shop")
sh.shardCollection("shop.products", { product_id: "hashed" })

// Вторичные индексы под поиск по каталогу
db.products.createIndex({ category: 1, price: 1 })
```

Обоснование:

- Самые частые и чувствительные к задержке операции - обновление остатка и
  карточка товара - идут по `product_id`, то есть остаются targeted: запрос
  попадает ровно в один шард.
- Hashed-стратегия равномерно размазывает высокий поток обновлений остатков по
  всем шардам, не создавая горячего шарда.
- Поиск по категории и цене реже и обслуживается вторичным индексом
  `{ category: 1, price: 1 }`. Такой запрос становится broadcast, но каждый шард
  отрабатывает его по индексу, а каталог обычно ещё и кешируется.

Альтернатива `{ category: 1, product_id: 1 }` (ranged) локализовала бы поиск по
категории, но дала бы jumbo-куски на популярных категориях и перекос записи -
поэтому отклонена.

## Коллекция orders

### Схема

```json
{
  "_id": "ObjectId",
  "order_id": "string (uuid)",
  "customer_id": "string (uuid)",
  "created_at": "Date",
  "items": [
    { "product_id": "string", "name": "string", "qty": "int", "price": "Decimal128" }
  ],
  "status": "string (created|paid|shipped|delivered|cancelled)",
  "total": "Decimal128",
  "geo_zone": "string"
}
```

### Операции и кандидаты в шард-ключ

Операции:

- Создание заказа со списанием остатков - очень высокая частота, вставка.
- История заказов клиента - высокая, по `customer_id` с сортировкой по `created_at`.
- Статус заказа - высокая, по `order_id`.

| Кандидат | Кардинальность | Частотность | Оценка |
| --- | --- | --- | --- |
| `created_at` | высокая | монотонный рост | плохо: hotspot на вставке |
| `geo_zone` | низкая (несколько зон) | высокая | плохо: jumbo-куски |
| `order_id` (hashed) | очень высокая | равномерная | targeted только по статусу, история становится broadcast |
| `{ customer_id: 1, created_at: 1 }` | высокая | равномерная по клиентам | хорошо |

### Решение: ranged по `{ customer_id: 1, created_at: 1 }`

```js
sh.shardCollection("shop.orders", { customer_id: 1, created_at: 1 })

// Уникальность бизнес-идентификатора заказа
db.orders.createIndex({ order_id: 1 }, { unique: true })
```

Обоснование:

- Префикс `customer_id` имеет высокую кардинальность и равномерно распределяет
  заказы по шардам - монотонного hotspot нет, потому что вставки разных клиентов
  попадают в разные куски.
- История заказов клиента (`find({ customer_id })` с сортировкой по
  `created_at`) - targeted-запрос по префиксу ключа: идёт в шарды одного
  клиента и уже отсортирован по второму полю ключа.
- Внутри одного клиента `created_at` растёт монотонно, но это не создаёт
  глобального hotspot, так как горячим был бы максимум один клиент.
- Статус по `order_id` остаётся broadcast, но это приемлемо: операция лёгкая
  (один документ по уникальному индексу на каждом шарде), а сразу после
  оформления статус обычно смотрят в контексте сессии, где `customer_id` известен
  и запрос становится targeted.

Альтернатива hashed `order_id` сделала бы targeted только просмотр статуса, но
превратила бы основную операцию (историю клиента) в broadcast - поэтому
отклонена.

## Коллекция carts

### Схема

```json
{
  "_id": "ObjectId",
  "user_id": "string | null",
  "session_id": "string | null",
  "items": [
    { "product_id": "string", "quantity": "int" }
  ],
  "status": "string (active|ordered|abandoned)",
  "created_at": "Date",
  "updated_at": "Date",
  "expires_at": "Date (TTL)"
}
```

```js
// Автоочистка старых корзин: документ удаляется, когда наступает expires_at
db.carts.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 })
```

### Операции и кандидаты в шард-ключ

Операции:

- Создание корзины - высокая частота, вставка.
- Получение активной корзины - очень высокая, по `{ session_id, status }` или `{ user_id, status }`.
- Добавление/замена/удаление товара - очень высокая, по `_id` корзины.
- Слияние гостевой в пользовательскую - средняя, чтение по `session_id`, запись по `user_id`.
- Отметка корзины как заказанной - средняя, по `_id`.

Особенность: корзину ищут то по `session_id` (гость), то по `user_id`
(залогиненный). Ни одно из этих полей не присутствует во всех документах, и у
них нет общего префикса. Шардирование по `user_id` отправило бы всех гостей
(`user_id: null`) в один кусок, по `session_id` - так же поступило бы с
пользовательскими корзинами без сессии. Оба варианта дают перекос.

### Решение: hashed по `_id`

```js
sh.shardCollection("shop.carts", { _id: "hashed" })

// Индексы под поиск активной корзины
db.carts.createIndex({ session_id: 1, status: 1 })
db.carts.createIndex({ user_id: 1, status: 1 })
```

Обоснование:

- `_id` (ObjectId) есть у каждого документа и максимально кардинален. Hashed
  убирает монотонность ObjectId и равномерно распределяет высокий поток создания
  и обновления корзин по всем шардам.
- Операции по `_id` (изменение состава, отметка `ordered`) остаются targeted.
- Получение активной корзины и слияние идут по `session_id`/`user_id` и
  становятся broadcast. Это приемлемо именно для корзин: коллекция мала и
  ограничена сверху TTL (старое автоматически удаляется), а каждый шард
  отрабатывает запрос по вторичному индексу. Стоимость broadcast по нескольким
  шардам на маленькой коллекции невелика.

Альтернатива (если broadcast на горячем чтении активной корзины окажется
дорогим): ввести денормализованное поле `owner_key = user_id ?? session_id` и
шардировать hashed по нему, переписав запросы получения корзины на фильтр по
`owner_key`. Тогда чтение активной корзины станет targeted, ценой
дополнительного поля и поддержки его согласованности при слиянии.

## Сводная таблица решений

| Коллекция | Шард-ключ | Стратегия | Почему |
| --- | --- | --- | --- |
| `products` | `{ product_id: "hashed" }` | hashed | Равномерное распределение частых обновлений остатков; карточка и обновление по `product_id` targeted |
| `orders` | `{ customer_id: 1, created_at: 1 }` | ranged | История клиента targeted и отсортирована; нет глобального hotspot вставки |
| `carts` | `{ _id: "hashed" }` | hashed | Равномерное распределение высокого потока записи; операции по `_id` targeted; broadcast-чтения дёшевы на TTL-коллекции |

## Риски и мониторинг

| Метрика | Где смотреть | Действие при проблеме |
| --- | --- | --- |
| Распределение кусков по шардам | `sh.status()`, `db.collection.getShardDistribution()` | Перекос - проверить кардинальность/частотность ключа, при необходимости refine shard key |
| Jumbo-куски | `sh.status()` (флаг jumbo) | Кусок не дробится из-за низкой кардинальности ключа - добавить более кардинальное поле в ключ |
| Доля targeted vs broadcast запросов | `mongos` лог, `explain()` (`SHARD_MERGE` vs `SINGLE_SHARD`) | Рост broadcast - пересмотреть запросы/индексы или шард-ключ |
| Hotspot на запись | метрики по шардам (opcounters, нагрузка CPU/диска) | Один горячий шард - признак монотонного ключа, перейти на hashed |
| Активность балансировщика | `sh.isBalancerRunning()`, лог миграций | Постоянные миграции - ключ даёт неравномерный рост, пересмотреть стратегию |
| Работа TTL (`carts`) | размер коллекции, `serverStatus().metrics.ttl` | Коллекция растёт - проверить индекс `expires_at` и фоновый TTL-монитор |

# Задание 8. Выявление и устранение горячих шардов

Раздел описывает, как обнаруживать "горячие" шарды в кластере MongoDB магазина
"Мобильный мир", какие метрики для этого собирать и какими механизмами
перераспределять нагрузку. Отдельно разбирается исходный инцидент: категория
"Электроника" дала 70% запросов и перегрузила один шард.

## Два типа перекоса

"Горячий" шард - это узел, нагрузка на который непропорционально выше, чем на
остальные. Важно различать причину, потому что лечатся они по-разному.

| Тип перекоса | Что перекошено | Типичная причина | Чем лечить |
| --- | --- | --- | --- |
| **Data skew** (перекос данных) | Объём данных и кусков на шарде | Низкокардинальный или частотный шард-ключ, jumbo-куски | Балансировщик, выбор/refine шард-ключа, resharding |
| **Load skew** (перекос нагрузки) | Поток операций (ops/sec), а не объём | Популярные документы, hot range на запись/чтение | Hashed-ключ, кеш, зоны, чтение с реплик |

Инцидент с "Электроникой" - это в первую очередь **load skew**: данные могли
быть распределены равномерно, но 70% операций били в куски с популярными
товарами. Поэтому решать его только балансировщиком (он выравнивает количество
данных, а не нагрузку) недостаточно.

## Почему выбранный шард-ключ уже снижает риск

В задании 7 для `products` выбран `{ product_id: "hashed" }`. Hashed-ключ
равномерно размазывает документы по шардам, поэтому товары категории
"Электроника" физически лежат на **разных** шардах, а не в одном диапазоне. Это
устраняет старый сценарий, где ranged-ключ `{ category: 1, ... }` собирал всю
"Электронику" в один кусок на одном узле.

Остаточный риск: **отдельный** сверхпопулярный товар (один документ) всё равно
живёт в одном куске на одном шарде. Шквал запросов к флагманскому смартфону
концентрируется на этом узле. Это уже не "горячая категория", а "горячий
документ", и для него нужны кеш и реплики (см. раздел про load skew).

## Набор метрик мониторинга

Метрики делятся на три уровня: распределение данных, нагрузка по шардам,
активность балансировщика. Источники - `mongos`, `serverStatus`, профайлер и
экспортёр в Prometheus/Grafana (`mongodb_exporter`).

### 1. Распределение данных и кусков

| Метрика | Где смотреть | Порог тревоги |
| --- | --- | --- |
| Кол-во кусков на шард | `sh.status()`, `db.coll.getShardDistribution()` | Разброс между шардами > 1 куска при остановленном балансировщике |
| Объём данных на шард (data size, %) | `getShardDistribution()` | Доля шарда заметно выше `100% / N_шардов` |
| Наличие jumbo-кусков | `sh.status()` (флаг `jumbo`) | Любой jumbo-кусок |
| Кол-во документов на шард | `getShardDistribution()` | Сильный перекос при равномерном по объёму |

```js
// Распределение конкретной коллекции по шардам
use shop
db.products.getShardDistribution()

// Вывод (сокращённо):
// Shard shard01 contains 41.2% data, 39.8% docs, 512 chunks
// Shard shard02 contains 58.8% data, 60.2% docs, 731 chunks  <- перекос
```

### 2. Нагрузка по шардам (главное для load skew)

Объём данных может быть ровным, а операции - нет. Эти метрики снимаются с
каждого `mongod`-шарда отдельно и сравниваются между собой.

| Метрика | Источник | О чём говорит |
| --- | --- | --- |
| `opcounters` (query/insert/update) на шард | `db.serverStatus().opcounters` | Прямой показатель потока операций; разъезд между шардами = load skew |
| Доля targeted vs broadcast | лог `mongos`, `explain()` (`SINGLE_SHARD` vs `SHARD_MERGE`) | Рост broadcast - запросы без шард-ключа бьют по всем узлам |
| CPU / load average шарда | `mongodb_exporter`, node_exporter | Один узел в потолке при простаивающих остальных |
| Очередь и блокировки | `serverStatus().globalLock`, `wiredTiger.concurrentTransactions` | Перегруженный шард копит очередь запросов |
| Давление на кеш (WiredTiger) | `serverStatus().wiredTiger.cache` | Вытеснение "грязных" страниц - признак горячего узла |
| p95/p99 latency по операциям | профайлер, `mongostat`, `mongotop` | Рост хвоста латентности на конкретном шарде |
| Топ горячих документов/коллекций | `mongotop`, профайлер (`system.profile`) | Выявление конкретного hot-документа (флагманский товар) |

```js
// Включить профайлер на медленные операции (> 50 мс) на шарде
db.setProfilingLevel(1, { slowms: 50 })

// Найти самые частые фильтры за последнее время
db.system.profile.aggregate([
  { $group: { _id: "$query.filter", n: { $sum: 1 }, avgMs: { $avg: "$millis" } } },
  { $sort: { n: -1 } },
  { $limit: 10 }
])
```

```bash
# Какие коллекции съедают время чтения/записи на узле (раз в 2 сек)
mongotop --host shard02-primary 2

# Сводка op/s, очередей, использования по кластеру
mongostat --host mongos 2
```

### 3. Активность балансировщика

| Метрика | Где смотреть | Сигнал |
| --- | --- | --- |
| Балансировщик запущен | `sh.isBalancerRunning()`, `sh.getBalancerState()` | Отключён при перекосе - включить |
| Кол-во и длительность миграций | `config.changelog`, `config.migrations` | Постоянные миграции - ключ даёт неравномерный рост |
| Незавершённые/висящие миграции | `config.migrations` | Миграция зависла - блокирует балансировку |
| Окно работы балансировщика | `config.settings` (`_id: "balancer"`) | Балансер выключен бизнес-окном в часы нагрузки |

```js
sh.isBalancerRunning()
sh.getBalancerState()

// История миграций за сутки
use config
db.changelog.find({ what: /moveChunk/, time: { $gt: new Date(Date.now() - 864e5) } })
                       .sort({ time: -1 })
```

### Алертинг (примерные правила)

- `max(opcounters_шард) / avg(opcounters_по_кластеру) > 1.5` в течение 5 минут -
  load skew, тревога.
- `max(data_size_шард%) - min(data_size_шард%) > 20` - data skew.
- Появился любой `jumbo`-кусок - тревога.
- Доля broadcast-запросов растёт неделя к неделе - ревизия запросов/индексов.

## Механизмы устранения дисбаланса

Дальше - по нарастанию "тяжести": от штатной балансировки до пересборки
шард-ключа. Лечим строго под тип перекоса, который показали метрики.

### A. Балансировщик кусков (data skew)

Балансировщик сам выравнивает **количество** кусков между шардами. Нужно лишь
убедиться, что он включён и не выключен бизнес-окном в часы нагрузки.

```js
sh.startBalancer()
sh.enableBalancing("shop.products")

// Окно работы: например, балансировать только ночью, чтобы миграции
// не конкурировали с пиковой нагрузкой днём
use config
db.settings.updateOne(
  { _id: "balancer" },
  { $set: { activeWindow: { start: "01:00", stop: "06:00" } } },
  { upsert: true }
)
```

Балансировщик НЕ помогает при load skew: он считает куски, а не запросы.

### B. Дробление и разгон jumbo-кусков

Jumbo-кусок не мигрирует и копит данные на одном шарде. Если кардинальность
ключа позволяет - дробим вручную; если нет - это сигнал к refine/resharding.

```js
// Принудительно разбить кусок по границе значения хеша/ключа
sh.splitFind("shop.products", { product_id: "ELECTRONICS-FLAGMAN-001" })

// Снять флаг jumbo после успешного дробления
use config
db.chunks.updateOne({ _id: <chunkId> }, { $unset: { jumbo: "" } })
```

### C. Зоны (zone sharding) - управляемое размещение

Зоны привязывают диапазоны значений ключа к группам шардов. В нашем кейсе - чтобы
вынести "Электронику" на выделенные мощные шарды (нужна ranged-составляющая по
`category`, например отдельная коллекция/индекс под зоны) или развести данные по
геозонам.

```js
// Пометить шарды зонами
sh.addShardToZone("shard-electronics-01", "HOT")
sh.addShardToZone("shard-electronics-02", "HOT")
sh.addShardToZone("shard03", "COLD")

// Привязать диапазон ключа к зоне
sh.updateZoneKeyRange(
  "shop.products_by_category",
  { category: "Электроника" }, { category: "Электроника￿" },
  "HOT"
)
```

Плюс: горячая категория обслуживается выделенным железом, не мешая остальным.
Минус: ручное управление, риск перелить нагрузку на саму зону - нужен запас
шардов в зоне.

### D. Resharding - смена шард-ключа онлайн (MongoDB 5.0+)

Если метрики показывают, что сам ключ выбран неудачно (перекос системный, а не
разовый), ключ меняется без простоя командой `reshardCollection`. MongoDB
создаёт копию коллекции с новым ключом и переключается на неё.

```js
// Пример: уйти от перекошенного ключа к hashed-распределению
db.adminCommand({
  reshardCollection: "shop.products",
  key: { product_id: "hashed" }
})

// Прогресс
db.adminCommand({ currentOp: 1, "command.reshardCollection": { $exists: true } })
```

Стоит дорого (временно дублирует данные и поток записи), поэтому это крайняя
мера по результатам анализа, а не ежедневный инструмент.

### E. refineCollectionShardKey - добавить поле в ключ

Когда ключ в целом ок, но не хватает кардинальности (jumbo-куски), можно
**дополнить** его суффиксом без полной пересборки. Это дешевле resharding.

```js
// Должен существовать индекс с расширенным ключом как префиксом
db.products.createIndex({ product_id: "hashed", _id: 1 })
db.adminCommand({
  refineCollectionShardKey: "shop.products",
  key: { product_id: "hashed", _id: 1 }
})
```

### F. Лечение load skew на горячем документе

Балансировщик, зоны и resharding не помогают, когда "горячий" один документ
(флагманский товар). Здесь работает разгрузка чтений и записи:

| Мера | Как помогает | Где в нашем стеке |
| --- | --- | --- |
| **Кеш Redis** | Карточка и остаток популярного товара читаются из кеша, не доходя до шарда | Redis уже внедрён в заданиях 2-4 |
| **Чтение с реплик** (`readPreference: secondary`) | Запросы к каталогу размазываются по членам реплика-сета горячего шарда | Репликация настроена в задании 3 |
| **Декремент остатка через очередь/атомарно** | `$inc` по `product_id` остаётся targeted и дешёвым; пики сглаживает очередь | Очередь обработки заказов из кейса |
| **Денормализация горячих счётчиков** | Вынести быстро меняющийся остаток в отдельную лёгкую структуру | По необходимости |

```js
// Чтение каталога с вторичных узлов, чтобы не грузить primary горячего шарда
db.products.find({ category: "Электроника" })
           .readPref("secondaryPreferred")
```

## Алгоритм реагирования (runbook)

```
1. Алерт: шард горячий.
2. Смотрим тип перекоса:
   - разъехались data_size% по шардам?      -> data skew  -> шаги A/B
   - разъехались opcounters при ровных данных? -> load skew -> шаг 3
3. Load skew: mongotop/профайлер -> что горячее?
   - горячая категория/диапазон  -> зоны (C) или проверка ключа (D)
   - один горячий документ        -> кеш + чтение с реплик (F)
4. Метрики говорят, что виноват сам ключ (системный перекос)?
   - не хватает кардинальности    -> refineCollectionShardKey (E)
   - ключ принципиально неудачен   -> reshardCollection (D)
5. Фиксируем причину в постмортем, добавляем/уточняем алерт.
```

## Итоговая таблица: метрика -> диагноз -> действие

| Что видим | Диагноз | Действие |
| --- | --- | --- |
| Разброс data_size% между шардами, jumbo-куски | Data skew | Включить балансер (A), разбить куски (B), при системности - refine (E) |
| Один шард по opcounters/CPU выше прочих, данные ровные | Load skew по диапазону | Зоны (C), вынос горячей категории на выделенные шарды |
| `mongotop` показывает один горячий документ | Load skew по документу | Redis-кеш + чтение с реплик (F) |
| Растёт доля broadcast (`SHARD_MERGE`) | Запросы без шард-ключа | Ревизия запросов/индексов, при необходимости новый ключ (D) |
| Постоянные миграции в `changelog` | Ключ даёт неравномерный рост | Пересмотр шард-ключа: refine (E) или reshard (D) |
| Балансер выключен/вне окна в час пик | Балансировка не идёт | `sh.startBalancer()`, скорректировать `activeWindow` (A) |

# Задание 9. Настройка чтения с реплик и консистентность

Раздел определяет для коллекций `products`, `orders` и `carts`, какие операции
чтения можно разгрузить на secondary, какие обязаны идти на primary, и какая
задержка репликации при этом допустима. Решения опираются на операции и
шард-ключи из задания 7.

## Базовые понятия

В MongoDB направление чтения задаётся параметром `readPreference`, а гарантии
видимости данных - параметрами `readConcern` (что мы видим) и `writeConcern`
(когда запись считается завершённой). Чтение с secondary - это компромисс:
разгружаем primary горячего шарда, но получаем данные с задержкой репликации
(replication lag).

| readPreference | Куда идёт чтение | Когда применять |
| --- | --- | --- |
| `primary` | только primary | данные, где нужна строгая актуальность (read-after-write, деньги, остатки) |
| `primaryPreferred` | primary, при его падении - secondary | важные чтения, но лучше устаревшие, чем ошибка |
| `secondary` | только secondary | разгрузка primary, терпимо к lag |
| `secondaryPreferred` | secondary, при их отсутствии - primary | массовые чтения каталога, аналитика |
| `nearest` | ближайший по латентности узел | гео-распределённое чтение |

Ключевые уровни `readConcern`:

- `"local"` - вернуть то, что есть на узле, без гарантий долговечности. Самый
  быстрый, допускает чтение откатываемых данных.
- `"majority"` - вернуть данные, подтверждённые большинством узлов (не
  откатятся). Дороже, но безопасно для денег и заказов.
- `"linearizable"` - строгая линеаризуемость, только на primary, самый дорогой.

Замечание про consistency на secondary: `readConcern: "majority"` гарантирует,
что прочитанные данные не откатятся, но **не** гарантирует, что они свежие.
Свежесть ограничивается только величиной replication lag.

## Как ограничиваем допустимую задержку репликации

Задержку на конкретном чтении ограничиваем параметром `maxStalenessSeconds`:
secondary, отставший больше указанного порога, исключается из выбора. Минимально
допустимое значение - 90 секунд (ограничение драйвера). Это "потолок" допустимой
устарелости для данного чтения, а не целевой lag.

Целевой (нормальный) lag в кластере отслеживается метриками и держится в
пределах единиц секунд. Если реальный lag приближается к `maxStalenessSeconds`,
читатель автоматически уходит на менее отставшие узлы или на primary
(в режиме `*Preferred`).

```js
db.products.find({ category: "Электроника" })
  .readPref("secondaryPreferred", [], { maxStalenessSeconds: 90 })
```

## Коллекция products

Самая читаемая коллекция и главная цель разгрузки: именно каталог "Электроники"
давал 70% запросов в исходном инциденте. Частота обновлений документа товара
низкая (описание, цена), но поле остатка (`stock.qty`) меняется часто в пик
продаж и критично к актуальности.

| Операция чтения | Куда | readConcern | maxStaleness | Почему |
| --- | --- | --- | --- | --- |
| Каталог, листинг по категории | secondaryPreferred | local | 90 с | Массовое чтение, терпит секунды устарелости; разгружает primary горячего шарда |
| Карточка товара (описание, цена) | secondaryPreferred | local | 90 с | Описание и цена меняются редко, небольшой lag незаметен |
| Проверка остатка перед показом "в наличии" | primaryPreferred | local | - | Можно показать "почти актуально", но лучше primary, чтобы не завышать доступность |
| Финальная проверка остатка при оформлении заказа | **primary** | majority | - | Решение о продаже: читать устаревший остаток нельзя, иначе продадим недоступный товар |
| Резерв/списание остатка (`$inc` с условием) | **primary** | majority (+ writeConcern majority) | - | Это запись, идёт только на primary, должна быть подтверждена большинством |

**Допустимая задержка:** для каталога и карточек - до 90 секунд (на практике
держим единицы секунд). Для остатка в момент оформления - **нулевая**: только
primary, lag недопустим.

**Обоснование:** разнесли "витринное" чтение и "торговое". Цена и описание
меняются редко - их безопасно отдавать с secondary, это снимает основную массу
нагрузки с primary. Остаток же быстро меняется и финансово значим: продать товар,
которого нет (oversell), - прямой убыток. Поэтому финальная проверка наличия идёт
только с primary с `readConcern: "majority"`, а списание - атомарный `$inc` с
`writeConcern: "majority"`.

## Коллекция orders

Заказы создаются очень часто в пик, статус меняется по мере обработки. Здесь
важен сценарий read-after-write: пользователь, только что оформивший заказ,
должен сразу увидеть его в истории и с правильным статусом.

| Операция чтения | Куда | readConcern | maxStaleness | Почему |
| --- | --- | --- | --- | --- |
| Просмотр заказа сразу после оформления | **primary** | majority | - | Read-after-write: с secondary заказ может ещё не реплицироваться, пользователь увидит "заказа нет" |
| Текущий статус активного заказа (оплата, сборка) | primaryPreferred | majority | - | Пользователь следит за статусом в реальном времени, устаревший статус вводит в заблуждение |
| История прошлых заказов клиента | secondaryPreferred | majority | 90 с | Старые заказы неизменны, lag в секунды не важен; targeted по префиксу `customer_id` |
| Детали давно доставленного заказа | secondaryPreferred | majority | 90 с | Финальное неизменяемое состояние, можно читать с реплики |
| Аналитика, отчёты, выгрузки | secondary | majority | больше (минуты) | Не влияет на пользователя, намеренно уводим тяжёлые запросы с primary |

**Допустимая задержка:** для свежесозданного заказа и активного статуса - **0**
(primary). Для истории и завершённых заказов - до 90 секунд. Для аналитики -
минуты, она не интерактивна.

**Обоснование:** разделили заказы на "живые" и "архивные". Живой заказ участвует
в read-after-write, поэтому читается с primary - показать "заказ не найден" или
старый статус сразу после действия недопустимо. Завершённые заказы неизменяемы и
дают основной объём чтений - их безопасно и выгодно разгрузить на secondary. Везде,
кроме аналитики, держим `readConcern: "majority"`: заказы финансовые, читать
откатываемое состояние нельзя.

## Коллекция carts

Корзина - сессионные данные с очень частыми обновлениями (добавление и удаление
товаров) и сильным требованием read-after-write: пользователь должен видеть
ровно то, что только что положил. При этом данные приватны для сессии и
ограничены TTL.

| Операция чтения | Куда | readConcern | maxStaleness | Почему |
| --- | --- | --- | --- | --- |
| Получение активной корзины пользователя/сессии | **primary** | local | - | Read-after-write: после "добавить в корзину" нужен актуальный состав, иначе товар "пропадёт" |
| Чтение корзины при оформлении заказа | **primary** | majority | - | По корзине считаем сумму и резервируем остатки, нужна точная и неоткатываемая версия |
| Слияние гостевой корзины в пользовательскую | **primary** | majority | - | Объединяем два состояния и тут же пишем, нельзя потерять только что добавленное |
| Фоновая аналитика брошенных корзин | secondaryPreferred | local | больше (минуты) | Не интерактивно, точная свежесть не нужна |

**Допустимая задержка:** для всех пользовательских операций с корзиной -
**нулевая**, читаем только с primary. Для фоновой аналитики брошенных корзин -
минуты.

**Обоснование:** корзина - классический read-after-write сценарий с частыми
изменениями. С secondary пользователь рискует увидеть устаревший состав сразу
после действия (добавил товар - а его нет; удалил - а он на месте). При этом
корзина читается в контексте одной сессии, нагрузка не массовая, разгружать
primary за её счёт смысла нет. Поэтому почти всё остаётся на primary; на secondary
уводим только фоновую аналитику, где свежесть не важна.

## Сводная таблица

| Коллекция | Операция | primary / secondary | Допустимый lag |
| --- | --- | --- | --- |
| products | Каталог, листинг | secondaryPreferred | до 90 с |
| products | Карточка товара | secondaryPreferred | до 90 с |
| products | Остаток при оформлении | **primary** | 0 |
| orders | Заказ сразу после создания | **primary** | 0 |
| orders | Статус активного заказа | primaryPreferred | 0 |
| orders | История и завершённые заказы | secondaryPreferred | до 90 с |
| orders | Аналитика | secondary | минуты |
| carts | Активная корзина | **primary** | 0 |
| carts | Корзина при оформлении / слияние | **primary** | 0 |
| carts | Аналитика брошенных корзин | secondaryPreferred | минуты |

**Принцип:** на secondary уходит то, что (а) читается массово и (б) терпит
устарелость в секунды - каталог и архив заказов. На primary остаётся всё, что
участвует в read-after-write или в принятии финансовых/складских решений -
остатки при продаже, живые заказы, корзины.

## Мониторинг и действия при проблемах

| Метрика | Где смотреть | Порог / сигнал | Действие |
| --- | --- | --- | --- |
| Replication lag по членам | `rs.printSecondaryReplicationInfo()`, `mongodb_exporter` (`mongodb_mongod_replset_member_replication_lag`) | lag > целевых единиц секунд, приближается к 90 с | Проверить нагрузку и сеть secondary; чтения с `maxStalenessSeconds` сами уйдут на свежие узлы |
| Доля чтений на secondary | лог, `serverStatus().opcounters` по членам | Перекос: secondary простаивают, primary в потолке | Перевести подходящие чтения на `secondaryPreferred` |
| Oversell (продажа сверх остатка) | бизнес-метрика заказов vs остатки | Любой случай | Убедиться, что финальная проверка остатка идёт на primary с `majority` |
| Жалобы "не вижу свой заказ/корзину" | алерты поддержки, логи 404 на свежих сущностях | Появление | Проверить, что read-after-write операции не ушли на secondary |
| Здоровье членов реплика-сета | `rs.status()` (`stateStr`, `health`) | Член не `PRIMARY`/`SECONDARY` | При недоступности secondary режимы `*Preferred` уводят чтения на primary автоматически |

```js
// Текущий lag по secondary
rs.printSecondaryReplicationInfo()

// Состояние членов реплика-сета
rs.status().members.forEach(m => print(m.name, m.stateStr, m.optimeDate))
```

**Логика реагирования:** рост lag сам по себе не ломает корректность - чтения с
`maxStalenessSeconds` автоматически перестают ходить на отставшие узлы и при
необходимости падают на primary. Опасны не задержки, а ошибочное направление
критичного чтения (остаток при продаже, свежий заказ, корзина) на secondary -
это ловим бизнес-метриками oversell и жалобами на "исчезающие" данные, и чиним
возвратом такого чтения на primary.

# Задание 10. Миграция на Cassandra

## Задание 10.1. Какие данные переносим в Cassandra и почему

### Чем Cassandra полезна в нашем случае

Сайт упал из-за того, что MongoDB при добавлении шардов перераспределяла все
данные и тратила на это ресурсы в пик нагрузки. Cassandra добавляет узлы без
полного перераспределения, не имеет единого мастера (запись принимает любой узел)
и очень быстро пишет данные.

Но у неё есть ограничения, которые определяют, что переносить нельзя:

- нет транзакций и строгой согласованности по умолчанию (данные актуальны не сразу);
- плохо переносит частые изменения и удаления одних и тех же записей;
- читает только по заранее известному ключу, без сложных запросов.

Поэтому в Cassandra хорошо ложатся данные, которые **много пишутся, почти не
меняются после записи и читаются по ключу**. Плохо - данные, где нужны
транзакции и точная актуальность (деньги, остатки).

### Критичные данные магазина

| Данные | Чем критичны |
| --- | --- |
| Заказы и оплата | целостность (деньги) |
| Остатки товаров | целостность (нельзя продать то, чего нет) |
| Корзина | скорость, пользователь сразу видит изменения |
| История заказов | большой объём и скорость чтения |
| Сессии пользователей | скорость, высокая частота |

### Что переносим в Cassandra

| Данные | Почему подходит |
| --- | --- |
| **История заказов** | Завершённый заказ не меняется, объём только растёт, читается по клиенту. Точная актуальность не нужна |
| **Сессии пользователей** | Простой доступ по ключу, очень частая запись, у Cassandra есть автоудаление по сроку (TTL). Строгая согласованность не нужна |

### Что оставляем как есть

| Данные | Почему не в Cassandra |
| --- | --- |
| Активные заказы и оплата | нужны транзакции и точная актуальность - остаётся в MongoDB |
| Остатки товаров | частое изменение с риском продать лишнее - остаётся в MongoDB |
| Корзина | очень частые изменения и удаления, пользователь должен сразу видеть результат - остаётся в MongoDB |
| Каталог товаров | проблема в объёме чтения, а не записи - закрывается кешем (Redis) |

### Итог

В Cassandra переносим **историю заказов** и **сессии пользователей**: они много
пишутся, почти не меняются и не требуют строгой согласованности. Деньги, остатки
и корзину оставляем в MongoDB, где есть нужные гарантии целостности.

Модель данных и ключи для этих сущностей - в задании 10.2, стратегии целостности -
в задании 10.3.

## Задание 10.2. Модель данных и ключи

### Как Cassandra распределяет данные

Cassandra хеширует partition key и по полученному числу (токену) кладёт партицию
на узел. Узлы делят между собой кольцо токенов. При добавлении узла к нему
переезжает только часть диапазонов токенов, а не все данные - в этом отличие от
MongoDB, которая перераспределяла всё. Поэтому ключ важно выбирать так, чтобы:

- значений было много и они были разнообразными - тогда данные лягут ровно по узлам;
- одна партиция не разрасталась до огромного размера ("горячая" партиция тормозит
  узел и читается медленно).

Модель строим от запросов: в Cassandra читать можно только по partition key, поэтому
сначала смотрим, как данные будут запрашивать.

### История заказов

**Запрос:** показать заказы клиента, сначала новые.

Логичный partition key - `user_id`: заказы одного клиента лежат рядом, читаются
одним обращением. Но у активного покупателя за годы накопятся тысячи заказов, и
партиция разрастётся. Поэтому добавляем в ключ "корзину" по году (`bucket`) -
партиция ограничена заказами за один год. Внутри партиции сортируем по
`order_id` (timeuuid) по убыванию, чтобы свежие заказы шли первыми.

```cql
CREATE TABLE order_history (
    user_id     uuid,
    bucket      int,          -- год, ограничивает размер партиции
    order_id    timeuuid,     -- кластерный ключ, хранит и время заказа
    created_at  timestamp,
    total       decimal,
    status      text,
    items       text,         -- позиции заказа в JSON
    PRIMARY KEY ((user_id, bucket), order_id)
) WITH CLUSTERING ORDER BY (order_id DESC);
```

- **Partition key `(user_id, bucket)`** - много клиентов и годов, токены лягут ровно,
  размер партиции ограничен одним годом, "горячих" партиций нет.
- **Кластерный ключ `order_id DESC`** - заказы клиента сразу отсортированы, выборка
  последних заказов идёт без дополнительной сортировки.
- Чтение за год - одна партиция: `WHERE user_id = ? AND bucket = 2026`.

### Сессии пользователей

**Запрос:** получить сессию по её идентификатору (по токену из cookie).

Partition key - сам `session_id`. Это случайный UUID, поэтому значения уникальны и
распределяются по узлам идеально ровно, "горячих" партиций быть не может. Кластерный
ключ не нужен: в партиции всего одна сессия. Срок жизни задаём через TTL - Cassandra
сама удалит протухшие записи, чистить вручную не надо.

```cql
CREATE TABLE user_sessions (
    session_id  uuid,
    user_id     uuid,
    created_at  timestamp,
    data        text,         -- содержимое сессии в JSON
    PRIMARY KEY (session_id)
) WITH default_time_to_live = 86400;   -- автоудаление через сутки
```

- **Partition key `session_id`** - случайный UUID, идеально ровное распределение.
- **TTL 86400** - сессия живёт сутки и удаляется автоматически.
- Чтение - точечное по ключу: `WHERE session_id = ?`.

### Почему это минимизирует решардинг

Обе таблицы используют partition key с большим числом разнообразных значений
(`user_id` + год, случайный `session_id`). Токены распределяются ровно, и при
добавлении узла переезжает только небольшая доля диапазонов - полного
перераспределения, из-за которого падал сайт на MongoDB, не происходит. Ограничение
размера партиции у истории заказов (год) и точечный доступ у сессий гарантируют, что
нагрузка не сконцентрируется на одном узле в пик.

| Сущность | Partition key | Кластерный ключ | Защита от горячих партиций |
| --- | --- | --- | --- |
| История заказов | `(user_id, bucket=год)` | `order_id DESC` | партиция ограничена годом |
| Сессии | `session_id` | - | случайный UUID, ровное распределение |

## Задание 10.3. Стратегии целостности данных

Cassandra пишет одни и те же данные на несколько узлов (реплик). Из-за сбоев и
отложенной записи реплики могут разойтись. Есть три механизма, которые их
выравнивают.

### Чем отличаются механизмы

| Механизм | Когда срабатывает | Цена |
| --- | --- | --- |
| **Hinted Handoff** | при записи, если реплика недоступна: координатор хранит "подсказку" и досылает данные, когда узел вернётся | дешёвый, работает сам |
| **Read Repair** | при чтении: координатор сверяет реплики и на лету чинит устаревшие | небольшая добавка к latency чтения |
| **Anti-Entropy Repair** | вручную или по расписанию (`nodetool repair`): полная сверка всех данных через дерево хешей | тяжёлый, грузит диск и сеть |

Логика выбора простая:

- Hinted Handoff и Read Repair - лёгкие и точечные, лечат только то, что пишется и
  читается прямо сейчас. Их держим включёнными почти всегда.
- Anti-Entropy Repair - тяжёлый, но единственный, кто чинит "холодные" данные,
  которые давно не читали. Нужен только там, где данные живут долго и их нельзя
  потерять. Запускать обязательно в пределах `gc_grace_seconds`, иначе удалённые
  записи могут "воскреснуть".

### История заказов

Данные важные (заказы терять нельзя), живут долго, часто читаются клиентом.

| Механизм | Решение |
| --- | --- |
| Hinted Handoff | **да** - если реплика лежит во время записи, заказ не потеряется и догонит узел при восстановлении |
| Read Repair | **да** - заказы регулярно читают, при каждом чтении реплики сами выравниваются почти бесплатно |
| Anti-Entropy Repair | **да, по расписанию** (раз в неделю) - старые заказы перестают читать, и Read Repair их уже не чинит; плановый repair выравнивает "холодные" партиции и не даёт расхождениям копиться |

Уровень согласованности - `LOCAL_QUORUM` на запись и чтение: большинство реплик
подтверждает операцию, клиент видит актуальную историю. Чуть выше latency, но для
просмотра заказов это некритично, зато нет риска показать неполный список.

### Сессии пользователей

Данные временные (TTL сутки), теряются без последствий - пользователь просто
перелогинится. Каждый запрос читает сессию по `session_id`.

| Механизм | Решение |
| --- | --- |
| Hinted Handoff | **да** - дешёвый и включён по умолчанию, лишним не будет |
| Read Repair | **да** - сессию читают на каждом запросе, чтение само поддерживает нужную реплику в актуальном виде |
| Anti-Entropy Repair | **нет** - данные и так удалятся по TTL через сутки; гонять тяжёлый repair по тому, что скоро исчезнет, - пустая трата ресурсов |

Уровень согласованности - `ONE` на запись и чтение: отвечает первая же реплика,
минимальная latency. Для сессий это оправдано - скорость важнее точной
согласованности, а редкое расхождение лечится повторным логином.

### Итог и компромисс latency / согласованность

| Сущность | Hinted Handoff | Read Repair | Anti-Entropy | Уровень согласованности | Приоритет |
| --- | --- | --- | --- | --- | --- |
| История заказов | да | да | да, по расписанию | `LOCAL_QUORUM` | надёжность важнее скорости |
| Сессии | да | да | нет | `ONE` | скорость важнее надёжности |

Главный рычаг компромисса - уровень согласованности. Чем больше реплик должны
ответить, тем выше гарантия и выше задержка. Поэтому для важных и долгоживущих
заказов берём `QUORUM` и добавляем плановый repair, а для временных сессий -
`ONE` без тяжёлого repair, ради минимальной задержки.
