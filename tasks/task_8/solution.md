# Задание 8. Выявление и устранение «горячих» шардов

Документ описывает, как обнаруживать «горячие» шарды в кластере MongoDB
магазина «Мобильный мир», какие метрики для этого собирать и какими
механизмами перераспределять нагрузку. Отдельно разбирается исходный инцидент:
категория «Электроника» дала 70% запросов и перегрузила один шард.

---

## Два типа перекоса

«Горячий» шард - это узел, нагрузка на который непропорционально выше, чем на
остальные. Важно различать причину, потому что лечатся они по-разному.

| Тип перекоса | Что перекошено | Типичная причина | Чем лечить |
| --- | --- | --- | --- |
| **Data skew** (перекос данных) | Объём данных и кусков на шарде | Низкокардинальный или частотный шард-ключ, jumbo-куски | Балансировщик, выбор/refine шард-ключа, resharding |
| **Load skew** (перекос нагрузки) | Поток операций (ops/sec), а не объём | Популярные документы, hot range на запись/чтение | Hashed-ключ, кеш, зоны, чтение с реплик |

Инцидент с «Электроникой» - это в первую очередь **load skew**: данные могли
быть распределены равномерно, но 70% операций били в куски с популярными
товарами. Поэтому решать его только балансировщиком (он выравнивает количество
данных, а не нагрузку) недостаточно.

---

## Почему выбранный шард-ключ уже снижает риск

В задании 7 для `products` выбран `{ product_id: "hashed" }`. Hashed-ключ
равномерно размазывает документы по шардам, поэтому товары категории
«Электроника» физически лежат на **разных** шардах, а не в одном диапазоне. Это
устраняет старый сценарий, где ranged-ключ `{ category: 1, ... }` собирал всю
«Электронику» в один кусок на одном узле.

Остаточный риск: **отдельный** сверхпопулярный товар (один документ) всё равно
живёт в одном куске на одном шарде. Шквал запросов к флагманскому смартфону
концентрируется на этом узле. Это уже не «горячая категория», а «горячий
документ», и для него нужны кеш и реплики (см. раздел про load skew).

---

## Набор метрик мониторинга

Метрики делятся на три уровня: распределение данных, нагрузка по шардам,
активность балансировщика. Источники - `mongos`, `serverStatus`, профайлер и
экспортёр в Prometheus/Grafana (`mongodb_exporter`).

### 1. Распределение данных и кусков

| Метрика | Где смотреть | Порог тревоги |
| --- | --- | --- |
| Кол-во кусков на шард | `sh.status()`, `db.coll.getShardDistribution()` | Разброс между шардами > 1 куска при остановленном балансировщике |
| Объём данных на шард (data size, %) | `getShardDistribution()` | Доля шарда заметно выше `100% / N_шардов` |
| Наличие jumbo-кусков | `sh.status()` (флаг `jumbo`) | Любой jumbo-кусок |
| Кол-во документов на шард | `getShardDistribution()` | Сильный перекос при равномерном по объёму |

```js
// Распределение конкретной коллекции по шардам
use shop
db.products.getShardDistribution()

// Вывод (сокращённо):
// Shard shard01 contains 41.2% data, 39.8% docs, 512 chunks
// Shard shard02 contains 58.8% data, 60.2% docs, 731 chunks  <- перекос
```

### 2. Нагрузка по шардам (главное для load skew)

Объём данных может быть ровным, а операции - нет. Эти метрики снимаются с
каждого `mongod`-шарда отдельно и сравниваются между собой.

| Метрика | Источник | О чём говорит |
| --- | --- | --- |
| `opcounters` (query/insert/update) на шард | `db.serverStatus().opcounters` | Прямой показатель потока операций; разъезд между шардами = load skew |
| Доля targeted vs broadcast | лог `mongos`, `explain()` (`SINGLE_SHARD` vs `SHARD_MERGE`) | Рост broadcast - запросы без шард-ключа бьют по всем узлам |
| CPU / load average шарда | `mongodb_exporter`, node_exporter | Один узел в потолке при простаивающих остальных |
| Очередь и блокировки | `serverStatus().globalLock`, `wiredTiger.concurrentTransactions` | Перегруженный шард копит очередь запросов |
| Давление на кеш (WiredTiger) | `serverStatus().wiredTiger.cache` | Вытеснение «грязных» страниц - признак горячего узла |
| p95/p99 latency по операциям | профайлер, `mongostat`, `mongotop` | Рост хвоста латентности на конкретном шарде |
| Топ горячих документов/коллекций | `mongotop`, профайлер (`system.profile`) | Выявление конкретного hot-документа (флагманский товар) |

```js
// Включить профайлер на медленные операции (> 50 мс) на шарде
db.setProfilingLevel(1, { slowms: 50 })

// Найти самые частые фильтры за последнее время
db.system.profile.aggregate([
  { $group: { _id: "$query.filter", n: { $sum: 1 }, avgMs: { $avg: "$millis" } } },
  { $sort: { n: -1 } },
  { $limit: 10 }
])
```

```bash
# Какие коллекции съедают время чтения/записи на узле (раз в 2 сек)
mongotop --host shard02-primary 2

# Сводка op/s, очередей, использования по кластеру
mongostat --host mongos 2
```

### 3. Активность балансировщика

| Метрика | Где смотреть | Сигнал |
| --- | --- | --- |
| Балансировщик запущен | `sh.isBalancerRunning()`, `sh.getBalancerState()` | Отключён при перекосе - включить |
| Кол-во и длительность миграций | `config.changelog`, `config.migrations` | Постоянные миграции - ключ даёт неравномерный рост |
| Незавершённые/висящие миграции | `config.migrations` | Миграция зависла - блокирует балансировку |
| Окно работы балансировщика | `config.settings` (`_id: "balancer"`) | Балансер выключен бизнес-окном в часы нагрузки |

```js
sh.isBalancerRunning()
sh.getBalancerState()

// История миграций за сутки
use config
db.changelog.find({ what: /moveChunk/, time: { $gt: new Date(Date.now() - 864e5) } })
                       .sort({ time: -1 })
```

### Алертинг (примерные правила)

- `max(opcounters_шард) / avg(opcounters_по_кластеру) > 1.5` в течение 5 минут -
  load skew, тревога.
- `max(data_size_шард%) - min(data_size_шард%) > 20` - data skew.
- Появился любой `jumbo`-кусок - тревога.
- Доля broadcast-запросов растёт неделя к неделе - ревизия запросов/индексов.

## Механизмы устранения дисбаланса

Дальше - по нарастанию «тяжести»: от штатной балансировки до пересборки
шард-ключа. Лечим строго под тип перекоса, который показали метрики.

### A. Балансировщик кусков (data skew)

Балансировщик сам выравнивает **количество** кусков между шардами. Нужно лишь
убедиться, что он включён и не выключен бизнес-окном в часы нагрузки.

```js
sh.startBalancer()
sh.enableBalancing("shop.products")

// Окно работы: например, балансировать только ночью, чтобы миграции
// не конкурировали с пиковой нагрузкой днём
use config
db.settings.updateOne(
  { _id: "balancer" },
  { $set: { activeWindow: { start: "01:00", stop: "06:00" } } },
  { upsert: true }
)
```

Балансировщик НЕ помогает при load skew: он считает куски, а не запросы.

### B. Дробление и разгон jumbo-кусков

Jumbo-кусок не мигрирует и копит данные на одном шарде. Если кардинальность
ключа позволяет - дробим вручную; если нет - это сигнал к refine/resharding.

```js
// Принудительно разбить кусок по границе значения хеша/ключа
sh.splitFind("shop.products", { product_id: "ELECTRONICS-FLAGMAN-001" })

// Снять флаг jumbo после успешного дробления
use config
db.chunks.updateOne({ _id: <chunkId> }, { $unset: { jumbo: "" } })
```

### C. Зоны (zone sharding) - управляемое размещение

Зоны привязывают диапазоны значений ключа к группам шардов. В нашем кейсе - чтобы
вынести «Электронику» на выделенные мощные шарды (нужна ranged-составляющая по
`category`, например отдельная коллекция/индекс под зоны) или развести данные по
геозонам.

```js
// Пометить шарды зонами
sh.addShardToZone("shard-electronics-01", "HOT")
sh.addShardToZone("shard-electronics-02", "HOT")
sh.addShardToZone("shard03", "COLD")

// Привязать диапазон ключа к зоне
sh.updateZoneKeyRange(
  "shop.products_by_category",
  { category: "Электроника" }, { category: "Электроника￿" },
  "HOT"
)
```

Плюс: горячая категория обслуживается выделенным железом, не мешая остальным.
Минус: ручное управление, риск перелить нагрузку на саму зону - нужен запас
шардов в зоне.

### D. Resharding - смена шард-ключа онлайн (MongoDB 5.0+)

Если метрики показывают, что сам ключ выбран неудачно (перекос системный, а не
разовый), ключ меняется без простоя командой `reshardCollection`. MongoDB
создаёт копию коллекции с новым ключом и переключается на неё.

```js
// Пример: уйти от перекошенного ключа к hashed-распределению
db.adminCommand({
  reshardCollection: "shop.products",
  key: { product_id: "hashed" }
})

// Прогресс
db.adminCommand({ currentOp: 1, "command.reshardCollection": { $exists: true } })
```

Стоит дорого (временно дублирует данные и поток записи), поэтому это крайняя
мера по результатам анализа, а не ежедневный инструмент.

### E. refineCollectionShardKey - добавить поле в ключ

Когда ключ в целом ок, но не хватает кардинальности (jumbo-куски), можно
**дополнить** его суффиксом без полной пересборки. Это дешевле resharding.

```js
// Должен существовать индекс с расширенным ключом как префиксом
db.products.createIndex({ product_id: "hashed", _id: 1 })
db.adminCommand({
  refineCollectionShardKey: "shop.products",
  key: { product_id: "hashed", _id: 1 }
})
```

### F. Лечение load skew на горячем документе

Балансировщик, зоны и resharding не помогают, когда «горячий» один документ
(флагманский товар). Здесь работает разгрузка чтений и записи:

| Мера | Как помогает | Где в нашем стеке |
| --- | --- | --- |
| **Кеш Redis** | Карточка и остаток популярного товара читаются из кеша, не доходя до шарда | Redis уже внедрён в заданиях 2-4 |
| **Чтение с реплик** (`readPreference: secondary`) | Запросы к каталогу размазываются по членам реплика-сета горячего шарда | Репликация настроена в задании 3 |
| **Декремент остатка через очередь/атомарно** | `$inc` по `product_id` остаётся targeted и дешёвым; пики сглаживает очередь | Очередь обработки заказов из кейса |
| **Денормализация горячих счётчиков** | Вынести быстро меняющийся остаток в отдельную лёгкую структуру | По необходимости |

```js
// Чтение каталога с вторичных узлов, чтобы не грузить primary горячего шарда
db.products.find({ category: "Электроника" })
           .readPref("secondaryPreferred")
```

## Алгоритм реагирования (runbook)

```
1. Алерт: шард горячий.
2. Смотрим тип перекоса:
   - разъехались data_size% по шардам?      -> data skew  -> шаги A/B
   - разъехались opcounters при ровных данных? -> load skew -> шаг 3
3. Load skew: mongotop/профайлер -> что горячее?
   - горячая категория/диапазон  -> зоны (C) или проверка ключа (D)
   - один горячий документ        -> кеш + чтение с реплик (F)
4. Метрики говорят, что виноват сам ключ (системный перекос)?
   - не хватает кардинальности    -> refineCollectionShardKey (E)
   - ключ принципиально неудачен   -> reshardCollection (D)
5. Фиксируем причину в постмортем, добавляем/уточняем алерт.
```

## Итоговая таблица: метрика -> диагноз -> действие

| Что видим | Диагноз | Действие |
| --- | --- | --- |
| Разброс data_size% между шардами, jumbo-куски | Data skew | Включить балансер (A), разбить куски (B), при системности - refine (E) |
| Один шард по opcounters/CPU выше прочих, данные ровные | Load skew по диапазону | Зоны (C), вынос горячей категории на выделенные шарды |
| `mongotop` показывает один горячий документ | Load skew по документу | Redis-кеш + чтение с реплик (F) |
| Растёт доля broadcast (`SHARD_MERGE`) | Запросы без шард-ключа | Ревизия запросов/индексов, при необходимости новый ключ (D) |
| Постоянные миграции в `changelog` | Ключ даёт неравномерный рост | Пересмотр шард-ключа: refine (E) или reshard (D) |
| Балансер выключен/вне окна в час пик | Балансировка не идёт | `sh.startBalancer()`, скорректировать `activeWindow` (A) |
